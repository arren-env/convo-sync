## Assistant

The structure is sound: a small summary file per conversation in `.agents/context/`, linked to the full note by session id. But going by the numbers we just measured, it wouldn't save many tokens, and the hard part is deciding who writes it.

**Why the token savings would be small.** In the 97k Cursor case, the convo-sync output was 3.1k tokens per call. A good summary might be about 1k, which saves around 2k per call, or about 6k on that restore. The rest of the 97k was Cursor's fixed overhead and the earlier chat being re-sent, and a context file doesn't touch either.

**Who writes it is the real problem.** The hooks run plain Node with no model, so there are three options:

1. **Extract it mechanically in the hook.** Free and reliable, but it only captures facts: files edited, commands run, the last plan or todo list, the last answer. You'd get no "why we chose GitHub Actions" unless an agent wrote that down.
2. **Have the agent write it every turn.** You get a real summary, but you pay output tokens on every turn of every session to save a few at restore time. Agents also forget to do it, and each harness behaves differently, so it would be unreliable.
3. **Have the first agent that restores write it, and later ones reuse it.** That adds a write step to the restore turn. In Cursor one extra call cost about 32k, which is exactly what we just removed.

**It also goes stale.** The note changes after every turn, so each context file needs to record which version of the note it was built from and be thrown away when that changes. That's another moving part to keep in sync.

**Where it would genuinely help: quality on long sessions.** Today `context` keeps the first request and the latest messages, so a decision made in the middle of a 40-turn session is lost. A section listing "files changed, commands run, open todos" fixes that. Option 1 gives you that for free, and it could go straight into the existing note's frontmatter, or into `context`'s output, with no new folder or mapping to maintain.

Which matters more to you here: fewer tokens, or the next agent not missing decisions from the middle of long sessions?

## Assistant

A model can't use information it hasn't read, and reading costs tokens. So "whole context for almost zero" isn't possible. What you can get close to is paying only for what the agent actually needs, and only once. Ranked by what our measurements say would save the most:

**1. Fewer round trips. This is the biggest lever.**
Every tool call re-sends the whole prompt, which was about 32k tokens per call in Cursor. Today a restore takes 2–3 calls: load the skill, run `context`, answer. If a hook injected the context when the session starts, the agent could answer in one call. Claude Code supports adding context from a `SessionStart` hook. I'd have to check which of the other agents support that before promising it. Estimated saving: 30–60k per restore.

**2. Restore in a new chat.**
The earlier Appwrite work was re-sent on every call, up to 14k tokens each time. It costs nothing to fix: it's a habit, plus a line in the skill, which is already there.

**3. Trim the fixed overhead.**
Cursor sent 16.4k tokens on every call before the conversation even started, including 5.3k for the skill list and 3.6k for MCP tools. Disabling skills and MCP servers you don't use in that harness saves on every call of every chat, not just restores. That's a setup change on your side, not something convo-sync can do.

**4. Load on demand instead of upfront.**
Rather than printing about 3k tokens of digest, `context` could print a short index: one line per conversation with the agent, date, title and last status, roughly 100–200 tokens. A new `convo-sync search "<topic>"` command would then return only the matching passages from the full notes. The agent pays for the middle of a long conversation only when the question needs it. This is the closest thing to "near zero, but the whole history is reachable".

**5. A mechanical state summary, as discussed.**
A few lines per note listing files changed, commands run and open todos, pulled out by the hook at no model cost. The index from idea 4 can show it, so decisions from the middle of a session aren't lost.

**6. Prompt caching (limited).**
Providers charge less for repeated prompt content they've cached. My understanding is that Anthropic charges about a tenth of the normal input price for cached tokens, but verify that against current pricing docs. The catch is that a cache doesn't carry over between providers or models, so it doesn't help when you switch harnesses, which is exactly your case.

My recommendation is 4 plus 5: an index with state lines by default, and search for going deep. That cuts what convo-sync itself costs to near zero, and convo-sync can build all of it. Idea 1 saves more per restore but depends on each harness's hook support, so it needs research first. Ideas 2 and 3 cost nothing to try today.

t3code doesn't get near zero either. It sends a budgeted selection of whole messages (up to 16k tokens by default, against convo-sync's ~3k), plus a tool the new agent can use to fetch whatever was left out. I read this from its own docs on `main` and its PRs and issues, not from memory.

**What it does when you switch provider** (from [docs/user/portable-handoffs.md](https://github.com/pingdotgg/t3code/blob/main/docs/user/portable-handoffs.md)):

1. **No summary.** The doc says plainly that a handoff is "a budgeted selection, not an agent-written summary". It keeps the original request, the most recent messages and command outcomes. Each message is kept whole or left out, never cut mid-message.
2. **Default budget of 16,000 tokens.** It can be set between 1,024 and 64,000 with `T3CODE_CONTEXT_HANDOFF_TOKEN_CAP`. It counts one token per byte to be safe, and imported history has a separate 64,000-byte ceiling.
3. **Context arrives in the first turn.** t3code owns the harness, so the selection goes straight into the new provider's first prompt. There's no extra round trip to load a skill or run a command. Codex can receive the messages as real history when the installed version supports it; other providers get them as quoted context.
4. **Left-out messages stay reachable.** The handoff lists what it omitted, and the agent can fetch those with a `t3_thread_read` tool.
5. **It tried summarising and dropped it.** [PR #1911](https://github.com/pingdotgg/t3code/pull/1911) had the old provider run `/compact` and hand the summary over. It was closed without being merged.

**Problems they've hit:**
- Fetching left-out messages can cost far more than the handoff itself. In [issue #27072](https://github.com/pingdotgg/t3code/issues/27072), the recovery hint gave no starting point, so the agent read from the start of the thread. Ten reads pulled about 327,000 characters.
- Long command outputs blow the budget, so whole items get skipped ([#23820](https://github.com/pingdotgg/t3code/issues/23820), [#23821](https://github.com/pingdotgg/t3code/pull/23821)).

**What this means for convo-sync:**
- **Their main win is delivering context in the first prompt.** That's the round-trip saving from my earlier idea 1. convo-sync can only do it where an agent's hooks can inject context at session start, because it doesn't own the harness.
- **Their "references plus a read tool" is the same as idea 4** (index plus search). The lesson from #27072 is that the pointer must name exactly what was left out, so the agent fetches only that and doesn't scan from the start.
- **Keeping messages whole is worth copying.** Today `context` can cut the latest message mid-text.
- **Our default output is already about 5× smaller** than theirs.
