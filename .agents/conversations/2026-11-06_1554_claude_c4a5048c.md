- Same-day sessions sort in the order they started in Explorer, Obsidian and `ls`.
- The name stays stable, so links and git history don't break.
- It's still a start time. A session opened at 09:00 and used until 18:00 will sort before one opened at 14:00.

**Option B: put the last-updated time in the name.** I'd avoid this.
- The file would be renamed after every turn. That breaks Obsidian links, shows up in git as a delete plus an add, and creates rename races if two agents sync at once.

**What to handle if we do A:**

2. **Name pattern.** `NOTE_NAME` in [context.mjs:8](scripts/lib/context.mjs:8) has to accept both formats, or old notes drop out of `context`.
3. **Time format.** Use `HHmm` with no colons, since Windows doesn't allow colons in filenames. Use local time, the same as the date part today.
4. **Tests and docs.** `fileBaseName` tests, README and SKILL.md all spell out the current format.

For "which one is most recent" specifically, you could also sort Explorer by Date modified. That already works today because every sync rewrites the file.

## Assistant

The time is in the **local time zone of the machine that runs the sync**, and the filename doesn't record which zone that was.

`fileBaseName` in [render.mjs](scripts/lib/render.mjs:9) builds the name with JavaScript's `getHours()` and `getMinutes()`. Those use the zone of the Node process, which is the OS setting unless the `TZ` environment variable overrides it. The underlying timestamp in the transcript is UTC. For example, a session that started at `2026-11-06T09:02Z` gets `_1432_` on a machine set to IST (UTC+5:30) and `_0902_` on one set to UTC. The date part already worked this way before this change. The `created` and `updated` fields in the frontmatter are also local time with no zone offset.

**Where this matters:**
- **People in different time zones.** If teammates in different zones commit notes to the same repo, the names sort correctly within each person's notes but not across people. One person's 14:32 can be another's 09:02.
- **Changing the machine's time zone.** If you change the zone or travel, and an existing session syncs again, it gets a new name. The old file is left behind as a duplicate, because the migration only handles the old date-only name, not a different time.
- **Daylight saving.** Times shift by an hour across a daylight-saving change. India has no daylight saving, so if you're in IST this won't affect you.

If everyone using the repo is in one time zone, local time is the more readable choice and I'd leave it. If notes are shared across zones, switch to UTC and mark it in the name, e.g. `2026-11-06_0902Z_claude_….md`. That gives the same order on every machine, but you'd have to convert the times in your head. Either way, it would be worth recording the offset in the frontmatter (`created: 2026-11-06 14:32:10 +05:30`) so the times aren't ambiguous.

Do you want me to switch the names to UTC or add the offset to the frontmatter?
